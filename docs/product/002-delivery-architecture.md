# 002 — Delivery architecture

Status: Proposed. Created: 2026-09-06. Updated: 2026-09-06.

The public GitHub repository is approved and created. The proposed site architecture below supports [001 — Choices experience](001-choices-experience.md); the website is not yet implemented.

## Recommendation

Use Astro to generate the chapter pages and continuous reading content, with a browser-based scene controller for the guided, animated explanation. Publish the built site through GitHub Pages. This supports separate shareable chapters, rich animation, and optional deeper examples.

GitHub Pages serves HTML, CSS, and browser JavaScript, including sites generated by a build step. Public repositories are eligible on GitHub Free; private repositories require an eligible paid plan. A project site normally uses `https://<owner>.github.io/<repository>/`. [GitHub Pages overview](https://docs.github.com/en/pages/getting-started-with-github-pages/what-is-github-pages).

Multiple pages work directly: each generated page can have its own URL. GitHub documents adding pages through the site's directory structure. Publishing a selected build artifact also keeps research Markdown out of the deployed reading experience, although it remains visible in a public repository. [Creating a GitHub Pages site](https://docs.github.com/en/pages/getting-started-with-github-pages/creating-a-github-pages-site).

## Alternatives

| Approach | Fit | Trade-off |
| --- | --- | --- |
| Astro static pages with an interactive chapter experience | Recommended for guided visual explanations and continuous reading | Requires a build toolchain, scene state, and careful base-path handling |
| Plain HTML/CSS/JavaScript pages | Good for a tiny fixed site | Shared layouts and content conventions become manual as chapters grow |
| A client-routed single-page application | Appropriate if a persistent simulation becomes the main experience | Adds application state and direct-link hosting considerations without a current product need |

These are project judgments, not comparative benchmark claims. Astro's documented page routing and Markdown support establish the needed capabilities. [Astro pages](https://docs.astro.build/en/basics/astro-pages/), [Markdown content](https://docs.astro.build/en/guides/markdown-content/).

## Proposed site shape

| Route, before the hosting base path | Purpose |
| --- | --- |
| `/` | Brief introduction and entry to the choices subject |
| `/choices/` | Orientation and the chapter reading order |
| `/choices/your-future-options/` | Guided first chapter; named fragments identify scenes, such as `#one-skill-many-paths` |
| `/choices/your-future-options/read/` | Continuous reading and print view generated from the same authored content |
| `/choices/notes/` | Adult explanation, evidence limits, and source links |
| `/choices/daily-decisions/` | Follow-up chapter, added only when its content is complete |

The proposed source structure separates content, layout, and diagram behavior:

```text
docs/                         research, editorial reference, plans
src/content/chapters/          authored scenes, examples, notes, and metadata
src/pages/                    generated routes and entry pages
src/components/               scene controls, shared reading components, and diagrams
src/layouts/                  reading-page document and navigation
src/styles/                   named design tokens and typography
public/                       approved illustrations and static assets
e2e/                          reading, direct-link, and interaction checks
```

This is a future structure; these application directories do not exist yet. Choose exact package versions and the package manager when implementation starts. Local Bun availability is useful but does not require a Bun server in production.

## Guided chapter behavior

Keep the scene state explicit: selected starting age, current scene, optional example/deep dive, and any comparison within that scene. Use a query parameter for the selected example age and stable scene identifiers in the URL fragment; for example, `?age=40#one-skill-many-paths`. Restore the same authored example on direct navigation. Back/Next, browser history, replay, and returning from deeper content must agree about the current age and scene. Invalid or unsupported age values fall back to the introductory default without breaking the page; exact supported inputs are an implementation-plan decision.

Author a small set of life-stage examples instead of generating a personalized future at runtime. The age selector positions the marker and chooses an appropriate authored scenario. This remains compatible with static hosting and requires no personal history or backend.

Generate the guided and continuous reading views from the same authored explanations. Core text is available in static HTML. Use HTML/SVG for precise map geometry and labels, with browser animation for transitions. Select the animation library only after the motion study establishes the required effects; static hosting does not constrain animation quality.

Future video entries can reference a poster, video, captions, and transcript. No video service integration or generation pipeline is needed now. Optional clips must load on request and preserve the surrounding scene state.

## Publishing requirements

Use the current official Astro GitHub Pages workflow as the starting point. Configure `site` and the repository `base` path, and deploy only the generated output. Internal links and assets must work under the project subpath as well as during local preview. [Astro's GitHub Pages deployment guide](https://docs.astro.build/en/guides/deploy/github/).

Before publication, verify direct navigation and reload on every route and named scene, starting-age selection and fallback, Back/Next and browser history, opening/closing deeper examples, replay/skip, phone and desktop layout, keyboard navigation, diagram fallback, reduced motion, and source links. The main story must remain readable if the interactive script fails. Enable HTTPS and verify the actual published URL before reporting it as live.

Build output can include JavaScript that runs in the browser; it does not require server execution. Do not add a backend unless a future agreed feature requires one.

## Starter-kit findings

The local reference is `~/code/starter-kit`. Its README, workflow, setup checklist, Bun/React template, and relevant design references provide useful conventions, but copying the complete kit would introduce requirements unrelated to this project.

Retain the spec-first approach, focused reusable components, named design tokens, readable text, accessibility, visual inspection, and separate Git operations. Adapt those ideas to an illustrated reading experience.

Resolve these mismatches explicitly:

- The kit's separate planning repository conflicts with this project's requirement to keep research in `docs/`. Use one repository.
- The Phoenix/Postgres/Hetzner default and Bun server template do not match static GitHub hosting. Carry over no backend, database, or deployment scaffolding.
- The style-guide example uses 11–13px text in several roles, while its minimum-font-size reference requires at least 14px. The proposed child-facing design should use approximately 18–20px body text and at least 16px for meaningful diagram labels; verify readability in context.
- The kit includes historical hosting instructions and project-specific tooling. Recheck current official instructions at implementation time.
- Claude-specific hooks are not automatically applicable to every agent environment. Record required outcomes in repository instructions and use tools available in the active session.

## Quality work before implementation

1. Review the chapter proposal and sample voice.
2. Produce a storyboard and motion study of the opening, one branching diagram, a deeper example and return, and the ending at phone and desktop widths.
3. Test whether a reader can explain the core mechanism, a trade-off, and a way to recover from a setback.
4. Write the implementation plan around the selected storyboard, including routes, content fields, diagram states, and verification.
5. Implement and publish the first complete chapter, then develop the daily-decisions follow-up.

The research and proposal are the current deliverable. A task-by-task software implementation plan becomes useful once the teaching sequence and visual behavior are settled.
